# minitrigger

Biblioteca TypeScript de execução durável de tasks/workflows (BullMQ + Redis + Postgres), instalável como dependência.

- Especificação completa: `docs/SPEC.md` (**a seção 2 é fixa; não mudar sem perguntar ao dono**).
- Plano, grafo de tarefas e modelos por tarefa: `docs/PLAN.md`.
- **Estado atual e próximos passos: `docs/HANDOFF.md` (ler primeiro ao retomar).**
- Notas de API verificadas via Context7: `docs/research/api-notes.md`.
- Agents do projeto: `.claude/agents/mt-implementer.md`, `mt-reviewer.md`, `mt-fixer.md`.

## Comandos

```bash
pnpm infra:up            # Postgres 16 (localhost:54329) + Redis 7 (localhost:63799, noeviction)
pnpm typecheck && pnpm lint && pnpm test
pnpm test:unit           # só unitários, sem infra
pnpm test:integration    # precisa de infra
pnpm test:flushall       # FLUSHALL no Redis inteiro: projeto vitest isolado, só Redis local + NODE_ENV=test
pnpm build               # tsup → dist (ESM + CJS + d.ts)
```

Env de teste: `TEST_DATABASE_URL`, `TEST_REDIS_URL` (padrões apontam para o docker-compose).

## Decisões de arquitetura (resumo — detalhes em docs/SPEC.md §2)

1. Postgres é a fonte da verdade; BullMQ é só transporte. Enqueue perdido é recuperado pelo reconciler via `run_after`.
2. Durabilidade por replay com memoização; `SuspendSignal` interno; `Promise.allSettled` dos steps em voo antes de suspender; suspensão autoritativa.
3. `seq_index` atribuído na chamada; múltiplas esperas = "esperar todos"; resolvedores e transação de suspensão fazem `FOR UPDATE` na run. **Decisão do dono: só waitpoints aguardados bloqueiam a retomada** (token só conta depois do step `${nome}#wait`; `child_run`/`batch` sempre contam).
4. Retries pelo motor (`attempts: 1` no BullMQ); `attempt` só incrementa em falha ou stall; `maxDurationMs` por tentativa.
5. Aquisição atômica com `enqueue_seq`; escritas checam ownership com `FOR SHARE`; toda saída de `running` zera `execution_id`.
6. Stall por heartbeat no Postgres (HOT update só de `heartbeat_at`, `fillfactor=80`, `SET LOCAL statement_timeout`).
7. jobId `${runId}-${seq}` (sem `:`); remoção agressiva de jobs.
8. Fila `${prefix}-system` com worker próprio para ticks, expirações e retenção.
9. Idempotência em `idempotency_keys` (PK `(task_id,key)`), `ON CONFLICT ... WHERE expires_at < now() RETURNING`; namespace `__` reservado.
10. Waitpoints criados na mesma transação da causa; resultados de filhas/tokens lidos de `runs`/`waitpoints`, não copiados em `steps.output`.
11. Não-determinismo por nome × `seq_index`; `#` reservado (`${name}#wait`).
12. `Serializable<T>` + validação runtime; limites de payload/step/log separados; formato fixo de erro.
13. Sem estado global. 14. Conexões injetáveis (duplicate() do ioredis; só fecha o que criou). 15. schema/prefix validados.
16. Advisory locks: `(hashtext(schema),1)` migrations (xact), `(hashtext(schema),2)` líder (client dedicado).
17. Tempo sempre do banco. 18. Migrations embutidas no bundle. 19. Cliente/worker separados. 20. Stop graceful devolve runs.
21. Schedules declarativos não apagam por padrão. 22. Checagens de ambiente indisponíveis são avisos.
23. Progresso por run: `ctx.progress.set` grava `runs.progress` (não é step), agrupado e sempre esvaziado antes de toda escrita terminal/suspensão.
24. Debounce por chave: `trigger(..., { debounce })` colapsa numa run `queued` pendente (sempre trailing); `payload: "first" | "last"` decide qual payload vence.
25. Concurrency key por fila: `queue: { concurrencyKey: { limit } }` + `trigger(..., { concurrencyKey })` limita `running` simultâneas da mesma chave; atraso cresce por tentativa `limited` (backoff 1s–30s).
26. Trigger transacional (outbox): `trigger(task, payload, { tx })` insere a run na transação do chamador; nada é enfileirado antes do commit; `LISTEN`/poll + adaptadores de ORM (`/typeorm`, `/knex`, `/drizzle`, `/prisma`) despacham depois.
27. Pausa de fila persistida no Postgres (`queue_state`), espelhada no BullMQ (`Queue.pause()`), ressincronizada pelo líder; `engine.queues.*`/`runs.cancelMany`/`retryFailed` para operações em lote.
28. Transporte Postgres (`transport: "postgres"`): fila = linha de `runs` com `SKIP LOCKED` (claim = `acquire`), `-system` = tabela `system_jobs` com fencing por `locked_by`, wake por `LISTEN/NOTIFY` (payload não confiável, agrupado) + poll adaptativo, pub/sub por `NOTIFY` só com id e sempre relido (cancel só aborta run `canceled`), `globalConcurrency` exato por advisory lock da fila, `cron-parser` para ticks (linha do tick nunca apagada); `prefix`/`redis`/`outbox`/`rateLimit`/streams são `ConfigError`; modo misto no mesmo schema recusado por `schema_meta`.

## Decisões de implementação

- **Biome 2.5.14** para lint e formatação (sem ESLint/Prettier), com a config do dono do projeto (tabs, lineWidth 100). `pnpm lint` = `biome check .`, `pnpm format` = `biome check --write .`. `useImportType` está desligado no Biome, mas `verbatimModuleSyntax` no tsconfig continua exigindo `import type`.
- **TypeScript 6.0.x** (não 7.x): o dts do tsup usa a API JS do compilador, que o TS 7 nativo não oferece.
- **ioredis ^5.11.1** como peer (não 6.x): o BullMQ 6.3.x é testado com ioredis 5.11.1 e seu adapter não trata RESP3, padrão do ioredis 6.
- **vite** como devDependency explícita: o `vitest.config.ts` tipa um plugin que carrega `.sql` como texto, espelhando o `loader: { ".sql": "text" }` do tsup.
- Imports: `import { Pool, escapeIdentifier } from "pg"` e `import { Redis } from "ioredis"` (named). O default import do ioredis não tipa com NodeNext + verbatimModuleSyntax.
- tsup `dts.compilerOptions.ignoreDeprecations: "6.0"`: o rollup-plugin-dts embutido no tsup 8.5.1 sempre define `baseUrl`, que o TS 6 transforma em erro.
- **Node `>=22` em runtime** (`"engines"` no `package.json`, `target: "node22"` no tsup), baixado de `>=24`: Node 20 chegou ao fim de vida em abril de 2026, e exigir 24 sem necessidade real de API/sintaxe exclusiva dele restringia consumidores à toa. Verificado que nada em `src/` depende de API exclusiva do Node 24: `pnpm build` roda igual e um smoke real (instalar o `.tgz` empacotado, `import`/`require`, e uma run real com `step.run`+`step.sleep` contra a infra docker) passa sob Node 22.13.1. As **ferramentas de dev continuam em Node 24** (`.node-version` fica `24`, é o que roda localmente/CI para tudo que não é o runtime publicado): `test/helpers/child/register-ts.mjs` (usado só por `test/integration/worker-close-spin.test.ts`, que precisa de um processo `node` de verdade fora do vitest) depende do type stripping nativo do Node para rodar `.ts` diretamente, que só vem ligado por padrão a partir do 23.6 — sob Node 22 esse arquivo específico falha sem a flag `--experimental-strip-types`, então a suíte completa (`pnpm test`) continua exigindo Node 24 no ambiente de desenvolvimento; é só o pacote publicado (o que roda em `dist/`) que suporta `>=22`.
- **Pacote publicado como `@rivia-labs/minitrigger`** (escopo npm), `publishConfig.access: "public"`. `repository`/`homepage`/`bugs` apontam para `https://github.com/igorabreu29/minitrigger` em HTTPS (não SSH), para funcionar sem chave configurada em qualquer ambiente que só lê metadados do pacote. Releases até `v0.2.0` (tag já publicada) foram empacotadas com o nome antigo, sem escopo (`minitrigger`); a partir de `v0.3.0` todo caminho de instalação (npm, tarball de GitHub Release, `pnpm add github:...`) usa o nome com escopo — ver `README.md` ("Install") para a nota sobre o que muda para quem ainda está preso a uma tag antiga.
- **Modo de teste (`createTestEngine`) movido para o subpath `@rivia-labs/minitrigger/testing`**, fora da entrada principal: `tsup.config.ts` tem duas entradas (`src/index.ts`, `src/testing/index.ts`) com `splitting: true`, então o código compartilhado (classes de erro, `createEngineCore`, o executor real que o modo de teste também usa para processar jobs) cai num chunk comum que as duas entradas importam — verificado que `instanceof NonDeterminismError`/`ConfigError`/etc. importado da entrada principal reconhece um erro lançado pelo código do subpath, em **ESM e CJS** (o splitting de CJS do tsup 8.5.1 é mais novo/menos testado que o de ESM; `scripts/check-pack.mjs` prova isso de verdade contra o pacote empacotado e instalado, não só contra `dist/` local). Sem essa garantia, bastaria o splitting falhar silenciosamente num dos formatos para duplicar as classes de erro e quebrar `instanceof` para quem importa `ConfigError` da entrada principal mas aciona o throw pelo subpath de teste. Consumidor que nunca importa `/testing` não paga pelo store/transporte/pubsub em memória no load nem no bundle da entrada principal (medido: ~2.3–2.8 ms de load "próprio" da entrada principal, sem contar `pg`/`bullmq`/`ioredis` já carregados, igual antes e depois do split — o ganho real é de tamanho: a entrada principal + seu chunk compartilhado somam ~259 KB não comprimidos contra ~321 KB do bundle único antigo que também embutia o backend em memória).
- Portas do docker-compose não padrão (54329/63799) para não colidir com serviços locais.

## Notas para as próximas fases (revisão da Fase 1)

- **Checagem de payload em `defineTask`:** `Serializable<P>` no parâmetro de `run` é ignorado (contravariância). A checagem tem de ficar no objeto de opções (ex.: `opts & ([Serializable<P>] extends [P] ? unknown : { __payloadNotSerializable: Serializable<P> })`) e/ou em `trigger(task, payload: P & Serializable<P>)`.
- Output `void` de task/step é gravado como `null`.
- Tasks genéricas (`<T extends Json>`) exigem cast; `any` passa como válvula de escape. Documentar no README (fase 10).
- Quando os tipos públicos referenciarem `pg.Pool`, adicionar `@types/pg` como peer opcional (`peerDependenciesMeta`).
- Instalação via GitHub com pnpm pode bloquear o `prepare` de dependências git; validar na fase 10.

- **`runs.created_at` truncado em milissegundos** (`date_trunc('milliseconds', now())`) em todo insert de run: o cursor `(created_at, id)` trafega como `Date` do JS; com microssegundos, a paginação pularia linhas. A store em memória (fase 9) deve seguir o mesmo.
- Cancelamento recursivo percorre descendentes nível a nível com `FOR UPDATE` (CTE recursiva não permite `FOR UPDATE`); ordem de locks pai → run → descendentes → waitpoints (ver `docs/store-contract.md`).
- Default de TTL de chave de usuário (`idempotencyKeyTtl`, 7 dias) é aplicado pela engine (fase 3), não pela store.

- Falha definitiva de uma run **não** cancela descendentes (filhas de `step.trigger` podem sobreviver ao pai, como na conclusão). Os waitpoints `pending` da própria run viram `timed_out` na mesma transação em **toda** saída terminal (`complete`, `fail`, `recoverStalled`→failed, `cancel`), e os jobs `wp-*-expire` deles são removidos (`expireJobsToRemove`, fase 5).
- Suspensão em `waiting_on_waitpoints` também faz `enqueue_seq + 1` (sem enqueue), para que uma reentrega do job antigo não readquira a run.

- Output de task é limitado por `maxPayloadBytes` (não `maxStepOutputBytes`): vai para `runs.output` e o pai o lê direto (decisão 10). Output inválido ou grande demais falha a run sem retry.
- Run de task desconhecida pelo processo (ex.: deploy em andamento) conta como tentativa com falha retryable.
- `stop()` devolve runs cuja função ignora o `signal`: semântica at-least-once (decisão 20); o resultado tardio é descartado pelo ownership.
- `@types/pg` é peer opcional: os tipos públicos citam `pg.Pool` e `Redis` do ioredis.

- Task sem parâmetro de payload tem payload `void` (opcional em `trigger`); `payload: unknown` explícito conta igual. Payload `undefined` é gravado como `null`.
- Valores alimentados em `setTimeout` (heartbeat, stall, shutdown, `maxDurationMs`) são limitados a 2^31-1 ms; delays do BullMQ não.

- **Fase 4 (steps):** `StepContext.register(kind, name)` é o ponto único de registro (checa step aninhado, erro fatal/suspensão/abort pendente, duplicata, atribui `seq_index` de forma síncrona, compara nome×índice e `kind` com o snapshot) e `start()` valida o nome do usuário e rastreia o step em `state.inFlight`; a fase 5 só adiciona tipos de step. Nomes internos (`${name}#wait`) usam `startInternal()` (pula `validateStepName`, mesmo registro + `trackInFlight`).
- **`steps.kind`** (`run`, `sleep`, `token`, `wait`, `trigger`, `trigger_wait`, `batch_wait`), `NOT NULL` + CHECK, adicionado **editando a migration 001** (pacote ainda não publicado; depois do primeiro release, mudanças de schema só em migrations novas). Gravado por `insertCompleted`/`insertWaitRef` (parâmetro `kind`), `insertSleep` (`sleep`), `triggerChildren` (por `mode`) e `createToken` (`token`); o replay compara o `kind` exatamente (ex.: `createToken("x")` trocado por `step.run("x")` → `NonDeterminismError`).
- `NonDeterminismError`, `DuplicateStepError`, `NestedStepError`, nome de step inválido (`validateStepName`, `ConfigError`) e argumento de step inválido (`fn` não-função em `step.run`, duração/`timeout`/`delay` inválidos em `sleep`/`createToken`/`trigger`/`triggerAndWait`/`batchTriggerAndWait`, `payloads` não-array em `batchTriggerAndWait` — todos `ConfigError`, marcados fatais no próprio `prepare()` do `step-context.ts` antes do `register()`) são bug de código: ficam em `state.fatalError` e falham a run **sem retry**, mesmo que o usuário capture o erro ou a execução suspenda depois. Depois disso, todo `step.*` relança o mesmo erro fatal (o código do usuário não consegue seguir executando steps). Task filha (`resolveTask` = `resolveChildTask` em `execute-run.ts`): registrada neste processo → usa o registro; senão o spec sai do próprio objeto passado (outro processo que tenha a task a executa; o transporte enfileira em fila não declarada). Objeto malformado (`id` não-string, `options` não-objeto), nome de fila inválido/`${prefix}-system`, `retry.maxAttempts` inválido e payload de filha não serializável ou acima de `maxPayloadBytes` (`childPayload`) também são fatais (`ConfigError`/`SerializationError`, sem retry).
- **Função que lança com steps em voo:** antes do `fail`/`retry`, o executor espera os steps em voo (`settleBeforeFail`, mesmo `drainInFlight`), **sem abortar** `ctx.signal`; heartbeat e `maxDurationMs` seguem ativos; a espera é limitada por `stallTimeoutMs` (revisão externa item 4: sem isso, um `Promise.race([ctx.step.run(...), prazo])` sem `maxDurationMs` segurava o slot do worker para sempre com o heartbeat vivo) — passado o limite, `warn` ("gave up waiting"), `ctx.signal` aborta com `"finished"` (a tentativa acabou) **antes** da escrita e a run falha/retenta com o **erro original**; `maxDurationMs` menor encerra antes; um `warn` (`runId`/`taskId`/`steps`) lista os nomes em voo antes de drenar, para uma run presa ficar diagnosticável. Step que completa é gravado (o retry o reaproveita pela memoização); timeout durante a espera encerra a espera e grava falha/retry com o **erro original** (não `TimeoutError`); step que suspende durante a espera é ignorado (o erro vence); **erro fatal não espera** (decisão do coordenador, desviando do plano original: `ctx.step.*` já se recusa a gravar depois de um erro fatal e a run falha sem retry de qualquer forma — esperar só atrasaria a escrita terminal e arrisca travar se o step em voo nunca assentar sozinho). Só `lost`/`canceled`/`shutdown`/`handedBack` pulam a espera (nada mais é gravado).
- **Steps aninhados não são suportados:** `ctx.step.*` chamado dentro do `fn` de um `step.run` lança `NestedStepError` (detectado com `AsyncLocalStorage` ativo só enquanto o `fn` roda). O `step.run` externo também não é gravado, mesmo que o `fn` capture o erro.
- **Timeout durante o `allSettled` pré-suspensão:** se `maxDurationMs` estoura depois que a execução suspendeu (esperando steps em voo), a suspensão vence (decisão 2): `runs.suspend` roda normalmente, `attempt` não incrementa e o step em voo que não terminou reexecuta no replay. Cancel/lost/shutdown nesse intervalo não gravam nada.
- **Concorrência e determinismo:** `seq_index` na chamada torna determinístico um `Promise.all` direto de steps. Mas ramos assíncronos concorrentes que chamam **mais** steps depois de um `await` (ex.: `Promise.all(items.map(async i => { await ctx.step.run(a); await ctx.step.run(b) }))`) registram esses steps na ordem de conclusão, que muda entre execuções, e podem gerar `NonDeterminismError` no replay. Regra: não chamar steps depois de `await` dentro de ramos concorrentes (vai para as "regras de ouro" do README na fase 10).
- Output de `step.run` é normalizado antes de devolver: `void` → `null` já na primeira execução (igual ao replay). Output inválido/grande (`SerializationError`) propaga para a função como erro comum.
- `sleep` no replay: vencido se `snapshot.now + tempo monotônico decorrido >= wake_at` (limite inferior do `now()` do banco); `completeSleep` re-checa no banco (`not_due` → suspende de novo). A suspensão corre na corrida da execução (`onSuspend`), sem esperar a função terminar; heartbeat e `maxDurationMs` seguem ativos durante o `allSettled`. Depois de `runs.suspend`, `ctx.signal` aborta com o novo `AbortKind` `"suspended"` para parar código que engoliu o sinal (`logger.warn`).
- Outputs adiados (`maxInlineStepOutputBytes`) carregam em lotes alinhados de 50 `seq_index` (`DEFERRED_OUTPUT_BATCH_SIZE`), compartilhados por steps concorrentes.
- `NonDeterminismError`, `DuplicateStepError` e `NestedStepError` são exportados por `src/index.ts`.

- **Fase 5 (tokens/subtasks):** `StepContextDeps.waits` (`StepWaitDeps`) é a costura do executor: `triggerChildren`/`listChildResults`, `createToken`/`getToken`, `resolveTask`, `enqueueRun` e `scheduleExpire` (esses dois nunca lançam; enqueue perdido fica para o reconciler). `waitForToken(name)` sem `createToken` na execução registra os dois steps (`name` + `name#wait`) de forma síncrona. Replay de wait: status do snapshot (`pending` → suspende direto; a transação de suspensão re-checa); resolvido → uma query (`getToken` ou `listChildResults`). No primeiro `waitForToken`, depois do `insertWaitRef` há um `getToken`: token já completado (run ainda `running`) retorna sem suspender.
- **Expiração:** `createToken`/`triggerChildren` agendam `wp-${id}-expire` com o delay do banco depois do commit. No replay, `createToken` re-adiciona o job se o token ainda está `pending` com `expires_at` (mesmo jobId → no-op do BullMQ; recria se o processo morreu entre commit e enqueue). `not_due` no handler: `job.moveToDelayed(Date.now() + delayMs_do_banco, job.token)` + `throw new DelayedError()` (mesmo jobId; re-adicionar o id do job ativo seria ignorado pelo BullMQ e um id novo escaparia da remoção pelos resolvedores). `createToken` na store é idempotente por `(run_id, step_name)`.
- `WaitResult` de timeout: `{ ok: false, error: { name: "Timeout", retryable: false } }`. Batch com timeout: só as filhas canceladas PELA expiração (`error.message === WAITPOINT_TIMEOUT_REASON`, constante em `store/types.ts`) viram `Timeout`; filhas que completaram, falharam ou foram canceladas por `runs.cancel(childId)` antes do timeout mantêm o resultado real. Filha cancelada → `error.name = "Canceled"`. `batchTriggerAndWait` com `[]` consome `seq_index`, não grava nada e devolve `[]`; número de filhas diferente do de payloads no replay → `NonDeterminismError`.
- `engine.tokens.complete(id, output)` → `{ completed: true }` ou `{ completed: false, reason: "not_found" | "completed" | "timed_out" | "run_finished" }` (id que não é UUID → `not_found`; `run_finished` quando o token está `timed_out` e a run dele é terminal, lido sob o `FOR UPDATE` da run no `completeToken`); `output` validado com `maxPayloadBytes` antes de tocar o banco. `step.trigger` aceita `{ delay }` (`TriggerChildrenInput.delayMs`).
- O reconciler (não ligado à engine ainda, fase 6) já remove `expireJobsToRemove` de `recoverStalled`→failed. No caso 5 (expiração) remove os jobs de run das filhas canceladas (`removeRunJob`, best-effort) e chama `onCanceled?(runIds)` (opção de `createReconciler`; a engine vai passar `cancelLocally` + pub/sub). Falha do hook é logada/contada em `errors` e não impede a retomada do pai.
- **Decisão do dono (decisão 3): só waitpoints aguardados bloqueiam a retomada.** Um `token` só conta como pendente para a retomada se existir o step `${step_name}#wait` (kind `wait`) da run; `child_run`/`batch` sempre contam (nascem com o step de espera). Fonte única: `blockingWaitpointExistsSql` (`store/sql/resolve.ts`), usada por `runs.suspend`, `applyResumeRule` e pelo reconciler (`listStaleWaiting`, `repairOrphanWaiting`). Assim `createToken("ok")` → `sleep("lembrete")` → `step.run` → `waitForToken("ok")` acorda depois do sleep sem o token. Completar um token ainda não aguardado enquanto a run dorme usa a regra de retomada normal (`run_after = max(wake_at)`), sem retomada adiantada.
- **Steps não aguardados:** se a função retorna com steps em voo (ex.: `void ctx.step.trigger(...)`), o executor loga `warn` (`step "x" was not awaited`) e faz o mesmo `allSettled` com abort de antes da suspensão (`drainInFlight`) antes do `complete`: o trigger cria a filha, o `step.run` é gravado. Se um desses steps suspender (`waitForToken`/`sleep`/`triggerAndWait` não aguardado), a suspensão vence (decisão 2): a run suspende em vez de completar e o replay devolve o output quando nada mais estiver pendente. Só no caminho `success`; erro/abort seguem como antes (escritas tardias caem no ownership). `ExecutionState.inFlight` virou `Map<Promise, nomeDoStep>`.

- **Fase 6 (resiliência ligada à engine):** `start()` sobe, depois dos workers, o subscriber de pub/sub (conexão dedicada `subscriber`) e o loop do líder (`setInterval` unref de `reconciler.intervalMs`, primeiro tick imediato, sem sobreposição: tick em andamento → o próximo é pulado). Tick: `leader.tryAcquire()`; só o líder roda `reconciler.runOnce()` e agenda a retenção. Depois de perder a liderança (`onLose`), o processo pula uma tentativa para dar a vez a outro. `stop()`: para o loop (espera o tick, `leader.close()`) antes de fechar os workers; `pubsub.close()` e flush das publicações pendentes no `beforeClose`.
- Client do líder: `connectionString` com `postgres` string, `() => new Client(pool.options)` com pool injetado (decisão 16). O líder segura uma conexão extra fora do pool.
- **Retenção:** job `retention` na `-system` com jobId `retention-${floor(now_do_banco_ms / retention.intervalMs)}` (decisão 17). Como os jobs são removidos ao completar, o jobId só deduplica entre processos enquanto o job existe; o processo guarda a última janela enfileirada. Qualquer worker `-system` executa o job, sem checar liderança: a varredura é idempotente (`SKIP LOCKED`), uma segunda na mesma janela (troca de líder) só custa queries.
- **Cancelamento entre processos:** `cancelLocally` (engine `runs.cancel`, expiração na `-system`) aborta locais, publica status e `publishCancel`; o `onCanceled` do reconciler aborta locais e publica. Toda engine iniciada assina `onCancel` → `abort("canceled")`. Engine só de disparo publica pela conexão compartilhada (`createPubSubPublisher`), sem assinar. `PubSub.ready` (o `start()` espera o `SUBSCRIBE`).
- **Status publicado (costura da fase 7):** `RunNotifier` (`executor/notify.ts`) nas transições: `queued` (trigger, filhas, retry, release/hand-back), `running` (acquire), `waiting`/`queued` (suspend), `completed`/`failed`/`canceled`, stall recuperado (`onStatusChange` do reconciler). `updatedAt` vem da linha do banco: do registro retornado (create/acquire) ou de um `store.runs.get` depois da transição (as outras operações da store não devolvem `updated_at`; se virar gargalo, fazer a store devolver `updatedAt`). Tudo best-effort, fora do caminho crítico, nunca falha a run.

  - **`schedule-tick` regravado no lugar, nunca apagado** (`upsertScheduleTick`/`rescheduleTick`): ao concluir ou esgotar as tentativas, um `UPDATE` fenced regrava a mesma linha (`job_id = 'schedule-tick:<id>'`) para a próxima ocorrência — nunca um `DELETE` + `INSERT` — então não existe uma janela em que o schedule não tem linha nenhuma, igual ao scheduler do BullMQ. `upsertScheduleTick` é um `INSERT ... ON CONFLICT (job_id) DO UPDATE ... WHERE data->>'cron' IS DISTINCT FROM EXCLUDED.data->>'cron' OR data->>'timezone' IS DISTINCT FROM EXCLUDED...`: regravar o mesmo padrão de cron/timezone é **no-op** para o tick pendente (`RETURNING (xmax = 0)` diz `created`/`updated`/`unchanged`), exatamente como o `upsertJobScheduler` do BullMQ — sem isso, todo `start()`/sync declarativo pularia um tick já vencido e ainda não processado. Um padrão que muda solta o lock (`locked_by = NULL`) e zera `attempts`; o worker que estivesse processando o tick antigo perde o fencing.
  - **`SystemJobDelayed`** (`src/executor/system.ts`, já existia como sinal interno do `not_due` da expiração de waitpoint): no modo Postgres é a própria classe usada pelo dispatcher — sem `bullmq`, não existe `DelayedError` para converter; `src/pg/workers.ts` trata `error instanceof SystemJobDelayed` como "já tratado" (`delay()` já rodou) em vez de contar como falha. No modo BullMQ, `src/queue/transport.ts` converte `SystemJobDelayed` em `DelayedError` na borda, como sempre.
  - **`NotifyBatcher`** (`src/pg/notify-batcher.ts`): agrupa toda publicação (`publishStatus`/`publishCancel`/o wake de fora da transação) numa janela curta (5 ms) ou 500 itens, deduplicado por `(canal, payload)`, e envia num único `SELECT pg_notify(c, p) FROM unnest($1::text[], $2::text[])` — evita pagar o lock global de commit do `NOTIFY` uma vez por transição de status (decisão 28(d)). Reaproveitado tanto pelo publicador do modo Postgres (`src/pg/pubsub.ts`) quanto, via `createPgListener` genérico (`src/pg/listener.ts`), pelo listener do outbox do modo BullMQ (decisão 26), que passou a usar o mesmo cliente genérico sem mudar de comportamento.
  - **Cancel relido, nunca confiado no payload do `NOTIFY`:** o assinante (`createPgPubSub`) recebe só o `runId` no canal de cancel e só aborta a execução local se essa run, relida do Postgres, está de fato `canceled` — um `NOTIFY` forjado com o id de uma run realmente em execução não a derruba (Review Focus 6, testado em Task 5 e Task 12). Status também relê antes de emitir (`runs.subscribe` mantém a mesma ordem obrigatória de sempre).
  - **`cron-parser` (dependência direta, fixada em `5.10.1` exato — a versão que o BullMQ fixa; revisão externa 5, item B7, com `test/unit/review5-cron-parser-pin.test.ts`)** substitui a regex própria de `src/schedules.ts` nos **dois** transportes (não só no Postgres): reconhece 5 ou 6 campos (segundos opcional no início); um padrão de 7 campos que a regex antiga deixava passar agora falha cedo com `ConfigError` (o BullMQ usa a mesma lib internamente, então esse padrão nunca funcionou de verdade — só antecipa o erro). Padrão vazio/só espaço é rejeitado explicitamente antes de chegar ao `cron-parser` (que leria `""` como "a cada minuto").
  - **`schema_meta`** (`src/store/sql/schema-meta.ts`, migration 009): `setIfAbsent(key, value)` é `INSERT ... ON CONFLICT (key) DO NOTHING RETURNING value`; quando nada é inserido (perdeu a corrida), o valor efetivo é relido numa **query nova** — nunca dentro do mesmo statement, que veria o snapshot de antes do commit concorrente. `assertSchemaTransport` (`src/backends/shared.ts`) chama isso com `key = "transport"` no `beforeStart` das duas fábricas de backend; um valor diferente do `resolved.transport` desta engine é `ConfigError` nomeando o modo em uso (guarda de modo misto). Engines 0.3.x nunca escrevem essa chave — documentado no README/CLAUDE.md como pré-requisito para migrar um schema de transporte.
  - **`recoverLostEnqueues`** (`src/reconciler.ts`, novo campo de `ReconcilerOptions`, default `true`): `false` no modo Postgres (passado por `createPostgresBackend`'s uso do reconciler) desliga os casos 1/2 (enqueue perdido) — nesse modo o `trigger()` é uma escrita atômica só (decisão 28(a)), então uma run vencida no `run_after` é backlog comum, não perda; o relatório do reconciler carrega `skippedLostEnqueues: true` quando desligado. Casos 3 (órfã `waiting` sem `run_after`), 4 (stall) e 5 (expirações) continuam iguais nos dois modos; o caso 5 remove a linha de `system_jobs` em vez de um job do BullMQ (mesma interface `removeSystemJob`).
  - **`RedisLike`** (`src/config.ts`): tipo estrutural mínimo (`duplicate`/`publish`/`on`) para `redis.connection` injetado — os tipos públicos nunca importam `ioredis`; `src/queue/connections.ts` (só alcançado pelo backend BullMQ) faz o cast de volta para um `Redis` real.
  - **`EngineConfig` união discriminada** (`src/config.ts`): `CommonConfig & (BullmqTransportConfig | PostgresTransportConfig)` — `redis`/`prefix`/`outbox` só existem no ramo `"bullmq"`, `polling` só no `"postgres"`; `resolveConfig` repete as mesmas checagens em runtime (`PermissiveConfig` interno) para quem monta a config em JS puro ou faz cast. `derivePoolMax(queues, systemConcurrency, transport)` centraliza a fórmula de `pool.max` (soma `systemConcurrency` só no modo Postgres, decisão 14) — usada tanto pela derivação própria do `createEngine` quanto por `warnPoolSizing`/`warnScaledPoolSizing` do backend, para as duas nunca discordarem.
  - **Autoteste de `NOTIFY`** (`awaitSubscriberReady` em `src/backends/postgres.ts`): depois da conexão `LISTEN` ficar pronta (limitada a 5 s; timeout é `MinitriggerError`, nunca `ConfigError` — infraestrutura transitória), um `pg_notify` de auto-teste no canal de wake precisa ecoar de volta em até 1 s; sem eco, só `warn` (pooler em modo transação na frente da conexão dedicada?) e o sistema segue só com o poll adaptativo (`polling.intervalMs`/`polling.jitterMs`).
  - **Debounce e o claim `SKIP LOCKED` (correção aplicada durante esta fase; só no modo Postgres desde a revisão externa 5, item B2 — flag `NewRunDebounce.releaseDue`, passado pela engine como `resolved.transport === "postgres"`; o BullMQ voltou ao comportamento da `main`, uma run pendente por chave, colapsando mesmo vencida):** no modo Postgres, uma run debounced pendente cujo `run_after` já venceu deixou de absorver triggers — o próximo trigger para a chave libera `debounce_key` da run vencida (nada mais nela muda) e abre uma nova run pendente. ## Benchmark

`pnpm bench` (`bench/run.ts`) roda contra a infra docker (`pnpm infra:up`) num schema/prefix
Postgres/Redis novo por execução (`mt_bench_<timestamp><random>`), depois derruba o schema
(`DROP SCHEMA ... CASCADE`) e faz `obliterate` de cada fila BullMQ que criou (as três filas de
task e `${prefix}-system`) — verificado sem sobra em `pg_namespace`/`redis-cli keys` após a
execução. Importa de `../dist/index.js` (saída buildada), não de `../src`: rodar `.ts` puro
funciona com o Node nativo (>=23.6 já tira tipos sem flag), mas todo import interno de `src/`
usa especificador `.js` (convenção NodeNext do projeto) que aponta para um arquivo `.ts`
adjacente — Node só faz esse remapeamento para especificadores sem extensão/`.ts`, não para um
`.js` literal — então `../src/index.js` não resolveria; o `dist/` buildado tem arquivos `.js`
reais batendo com cada especificador. O script `bench` roda `pnpm build` primeiro.

**Dois transportes (Task 10d/14, decisão 28):** `bench/run.ts` ganhou `--transport postgres|bullmq`
(padrão `bullmq`). Com `postgres`, o bench não usa `redis`/`prefix` nenhum (`transport: "postgres"`
explícito na config) e a limpeza é só `DROP SCHEMA ... CASCADE` (sem `obliterate` de fila BullMQ,
que não existe nesse modo).

Três fases medidas, cada uma limpa (não se sobrepõem):

1. **Throughput fim-a-fim**: 1.000 `trigger()` de uma task de 3 steps (`step.run` × 3, fila com
   `concurrency: 20`), relógio de parede do processo do disparo do primeiro `trigger()` até o
   último `run:completed` (via `engine.events.on`).
2. **Latência de retomada por sleep**: 30 runs de uma task com `step.sleep("1s")` + 1 step; tempo
   entre `runAfter` (o `wake_at`, lido do Postgres logo que a run suspende, evento `run:waiting`)
   e `updatedAt` do evento `run:completed` (Postgres também) — inclui o disparo do job atrasado do
   BullMQ, reaquisição da run e o step final trivial.
3. **Latência de retomada por token**: 30 runs de uma task suspensa em `waitForToken`; tempo entre
   a chamada `engine.tokens.complete(tokenId)` retornar (relógio do processo) e o evento
   `run:completed` chegar (mesmo processo, sem rede) — id do token lido de `runs.steps()` (o step
   `kind: "wait"` carrega `{ waitpointId }`).
